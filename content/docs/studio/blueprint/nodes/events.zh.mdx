事件 Head 是一张图的起点。它没有执行入口——运行时从 Head 进入这张图，执行链从`then`开始。本页其余内容都由这一点展开：Head 的数据输出就是这次事件的 payload，而你能用到哪些 Head，取决于蓝图挂在什么宿主上

## 约定

- **Head 没有执行入口。** 没有任何东西可以连进去。一张图里可以放多个 Head，各自的事件到达时各跑各的执行链。监听同一事件的所有 Head，不论在一张图还是多张图里，都在事件到达时同时开始，彼此不等待，其中一个出错也不会让其余的停下。游戏等待某个事件时（例如启动时等待 [`On Game Ready`](#on-game-ready)），等待的是全部 Head
- **数据输出就是 payload。** 除`then`以外的每个输出引脚，都按引脚 id 读取本次运行时事件 payload 的一个字段。派发没有设置的字段读到`null`——不是`0`，也不是`""`
- **坐标是设计坐标。** 元素的鼠标 Head 使用该元素自己的本地设计坐标系；因事件从后代元素[向上传递](#event-bubbling)而执行的 Head 也是如此，它读到的是这次按下在自己元素框内的位置，而不是在指针下那个元素框内的位置；放在 Surface 蓝图上的`Mouse Click`和`Right Click`则使用该 [Surface](/zh/docs/studio/blueprint/surfaces) 的设计坐标系
- **Blueprint Value 的 Head。** Blueprint Value 图只接受两个 Head：`Init`和`On Flush`
- **不可交互的元素不派发。** 控件处于禁用或文本编辑等不可交互状态时，完全不派发它的交互 Head

## 哪些 Head 可用

创建浮窗按蓝图 owner 过滤 Head。没有为你的 owner 列出的 Head，不是被某个开关藏起来了——在那里它根本不存在

| 宿主 | 提供的 Head |
| --- | --- |
| **应用逻辑**（`globalMain`） | `App Boot`、`On Game Ready`、`On Fullscreen Changed`、`On Window Focus Changed`、`On Window Close Requested`、`On Action`、四个键盘 Head、两个 preference Head |
| Surface 蓝图（`surfaceMain`） | `Surface Init`、`Surface Unmount`、`Before Surface Exit`、`After Surface Enter`、`Mouse Click`、`Right Click`、`On Fullscreen Changed`、`On Window Focus Changed`、`On Window Close Requested`、`On Action`、四个键盘 Head、两个 preference Head、两个 broadcast Head、`Element Flush`、`Element Click` |
| 控件私有蓝图（`widgetMain`） | 由该控件类型声明的能力决定，见下表 |
| 组件定义内的控件（`componentWidgetMain`） | `Init`、`On Flush`、`Unmount`、`Before Surface Exit`、`After Surface Enter`，以及下表中该控件类型声明的 Head。没有键盘、窗口、广播和绑定元素的 Head |
| Blueprint Value（`widgetValue`） | `Init`与`On Flush` |
| Story Action 蓝图 | `On Call` |

对控件来说，owner 只是规则的一半：每种内建控件都声明了一组事件能力，只有该控件自己列出的 Head 才会出现。这就是为什么`nl.list`没有`Mouse Enter`，而`nl.container`没有`Item Click`

| 控件类型 | Head |
| --- | --- |
| 所有支持私有蓝图的控件 | `Init`、`On Flush`、`Unmount`、`Before Surface Exit`、`After Surface Enter`、四个键盘 Head、`On Fullscreen Changed`、`On Window Focus Changed`、`On Broadcast`、`On Any Broadcast`、`Element Flush`、`Element Click` |
| `nl.container`、`nl.text`、`nl.image`、`nl.button`、`nl.dialog.sentence`、`nl.nvl.texts` | 九个鼠标 Head、`Focus`、`Blur`、`List Item Refresh` |
| `nl.video`、`nl.puppet` | 九个鼠标 Head、`Focus`、`Blur` |
| `nl.switch` | 九个鼠标 Head、`Focus`、`Blur`、`Changed`、`Turned On`、`Turned Off` |
| `nl.list`、`nl.notification.list`、`nl.choice.list`、`nl.nvl.list` | `Scroll`、`Scroll End`、`Item Render`、`Item Click`、`Item Hover`、`Selection Changed` |
| `nl.slider` | `Drag Start`、`Value Changed`、`Drag End` |
| `nl.textInput` | `Value Changed`、`Submit`、`Focus`、`Blur` |
| `nl.frame` | `Page Event` |

控件蓝图内部还有一层收窄：`List Item Refresh`只有当元素确实位于 List 的 item 模板之内时才提供

## 事件冒泡 [#event-bubbling]

有六个指针事件会沿元素树向上传递：`Mouse Click`、`Mouse Double Click`、`Mouse Down`、`Mouse Up`、`Mouse Wheel`和`Right Click`。事件从指针下的那个元素开始，依次经过每一层父元素，一直到该元素所在 Surface 的根元素。路径上每个拥有该事件 Head 的元素都会执行它，没有 Head 的元素被直接跳过。拥有 Head 的元素不会把事件留下，它的祖先的 Head 同样会执行。这些 Head 各自执行自己的链，所以不要让图依赖它们之中谁先执行

- **不向上传递的事件。** `Mouse Enter`、`Mouse Leave`和`Mouse Move`只留在指针所在的元素上。键盘、焦点、flush 和生命周期事件同样不向上传递，控件自己的事件（`Item Click`、`Value Changed`、`Changed`、`Submit`等）也不会
- **没有鼠标 Head 的控件。** List、Slider、文本输入框和 Frame 不提供鼠标 Head，会像任何没有 Head 的元素一样把这六个事件交给父元素，所以带`Mouse Wheel` Head 的容器能收到落在其内部 List 上的滚轮
- **离开 List。** 在 item 模板内部，Head 针对指针所在的那一行执行。事件向上离开 List 时，那一行就被留下了：List 之上的元素使用自己的变量，也读不到条目数据
- **离开组件。** 事件到达组件的根元素后，从摆放该组件的那个元素继续向上，所以容纳组件的容器能收到组件上的点击
- **Surface。** 到达 Surface 的点击还会执行 Surface 蓝图自己的`Mouse Click`或`Right Click`
- **Frame 中的 Page。** 落在 Frame 所显示 Page 的元素上的点击，向上传递到该 Page 的根元素为止：Frame 及其周围的元素收不到它。被显示的 Page 先以自己的设计坐标执行自己 Surface 的`Mouse Click`或`Right Click`，随后持有该 Frame 的 Surface 执行它自己的。落在被显示 Page 空白处的点击属于 Frame，并从 Frame 开始向上传递

图无法提前结束这次传递，[脚本](/zh/docs/studio/scripts)图层可以，用`ctx.stopPropagation()`：上层元素收不到这次事件，同一元素上的其他 Head 照常执行。同一元素上的 Head 同时开始，全部结束后事件才传到父元素。曾经用来控制冒泡的两个节点`Continue Event Bubble`与`Stop Event Bubble`已经被删除。它们真正被稳定用到的那一件事，也就是把窗口关闭挂住，现在由 App 分类下的 [`Keep Window Open`](/zh/docs/studio/blueprint/nodes/app) 负责，它只做这一件事

应用逻辑没有鼠标 Head。它通过 [`On Action`](#on-action) 收到指针输入，不论手势落在哪里，包括没有任何界面接收的地方：Page 只在绘有它的元素的地方接收点击，所以点在 Page 的空白处、或点在空无一物的舞台上，仍然会送达应用逻辑的`On Action` Head

Page 或图层播放退出动画期间，没有任何 Page 或图层接收的点击会被丢弃。它到不了游戏舞台和舞台上的游戏界面，因此不会推进剧情，应用逻辑也收不到。点在取而代之、正在进场的 Page 上的点击照常送达那个 Page。Frame 切换 Page 期间同理：进场 Page 的元素照常响应点击，而任何点击都不会越过 Frame，因此不会变成 Frame、它周围的元素或 Surface 上的点击

<Callout type="warn">
焦点位于文本输入元素时，按键不会送达任何蓝图：应用逻辑、Surface 和控件的键盘 Head 都不执行，也不会触发任何输入意图，所以输入名字时按 Space 不会推进对话、按 Escape 不会打开菜单。该输入框自己的`Value Changed`和`Submit`仍然照常触发
</Callout>

### On Game Ready

`blueprint.event.head.gameReady`

On Game Ready（游戏就绪时）在每个被接受的 NarraLeaf session 触发一次：此时`LiveGame`对象已创建并存入 Studio runtime，但`liveGame.newGame()`还没有启动第一段剧情

运行时把 NarraLeaf 环境初始化当作一个加载项，放在 **Surface 系统启动之前**：它以 Story 库默认 Story 的入口场景的 compiled story 挂载 Player，因此`LiveGame`已经存在、该场景资源开始预热，而玩家仍停留在主菜单。真正「进入游戏」只发生在`Start Game`或读档时，并且复用同一个已初始化的`LiveGame`：当`Start Game`的目标就是已预热的默认场景时为秒开，**不会**再次触发该 Head；只有`Start Game`指向不同场景时才会重新挂载环境并第二次触发。项目未配置默认 Story 时改为挂载一个空环境，该 Head 在启动时依然触发

| 引脚 | 方向 | 类型 | 说明 |
| --- | --- | --- | --- |
| `then` | out · exec | — | |

<Callout type="info">
把 NarraLeaf Preference 的初始化放在这里——`Set Auto Forward`、`Set Game Speed`、`Set Voice Volume`、`Set Sentence Speed`——这样它们在玩家进入游戏之前就已就绪。不要放在`App Boot`里：名字虽然像最早的钩子，它并不最先执行（`On Game Ready`先于它触发），而且它不保证此刻存在活动的 live game
</Callout>

### On Fullscreen Changed

`blueprint.event.head.fullscreenChanged`

On Fullscreen Changed（全屏状态变更时）在应用窗口进入或退出全屏时触发，包括在游戏之外切换全屏的情况。它先送达应用逻辑，再送达屏幕上的每个 Surface：从最上层开始的各图层、当前 Page、显示在 Frame 里的 Page，以及舞台上的游戏界面。在其中每个 Surface 上，放了该 Head 的控件蓝图也会执行。所以设置面板里的控件不必拥有整个 Page 也能跟随窗口状态

| 引脚 | 方向 | 类型 | 说明 |
| --- | --- | --- | --- |
| `then` | out · exec | — | |
| `isFullscreen` | out · data | `boolean` | 变化后的状态|

### On Window Focus Changed

`blueprint.event.head.windowFocusChanged`

On Window Focus Changed（窗口焦点变更时）在应用窗口获得或失去焦点时触发，例如玩家切到别的程序再切回来。桌面产物跟随自己的窗口，包括窗口被游戏之外的东西压到后面的情况；Web 导出跟随页面的可见性与焦点。它送达的蓝图和顺序都与`On Fullscreen Changed`相同。它与控件的`Focus`、`Blur` Head 无关，后两者说的是哪个控件持有键盘焦点

要在因别的原因执行的图里读取当前状态，用 [App 节点](/zh/docs/studio/blueprint/nodes/app)里的`Is Window Focused`

| 引脚 | 方向 | 类型 | 说明 |
| --- | --- | --- | --- |
| `then` | out · exec | — | |
| `isFocused` | out · data | `boolean` | 变化后的状态 |

### On Window Close Requested

`blueprint.event.head.windowCloseRequested`

On Window Close Requested（窗口关闭请求时）在玩家请求关闭窗口时触发。这次关闭会被挂起，先等应用逻辑、再按`On Fullscreen Changed`所述的顺序等屏幕上的每个 Surface 执行。其中任意一个执行了`Keep Window Open`就取消关闭，排在它之后的 Surface 不再被询问；没有则窗口继续关闭。在 Studio Dev Mode 中它覆盖 Dev Mode 窗口，在预览和正式产物中覆盖游戏窗口

只在应用逻辑和 Surface 蓝图中提供

| 引脚 | 方向 | 类型 | 说明 |
| --- | --- | --- | --- |
| `then` | out · exec | — | |

## 元素生命周期

### Init

`blueprint.event.head.init`

| 引脚 | 方向 | 类型 | 说明 |
| --- | --- | --- | --- |

### On Flush

`blueprint.event.head.flush`

On Flush（刷新时）在当前蓝图所属元素被蓝图 Host API 显式改写属性、并因此触发重绘时执行。渲染器自动计算的 CSS 状态样式（hover、focus 变体）不会触发它。在 Blueprint Value 中它兼作显式求值入口：默认 Dialog Nametag 就是靠这个入口在 Dialog 不重新挂载的情况下随对话推进刷新

Flush 是属性提交后的批处理通知。运行时按帧合并同一元素的 flush；flush 处理器内部再次改写该元素时，新的 flush 进入**下一帧**的批次——不存在同步重入

| 引脚 | 方向 | 类型 | 说明 |
| --- | --- | --- | --- |
| `then` | out · exec | — | |
| `element` | out · data | `element` | 被刷新的元素引用|

## 键盘 [#keyboard]

键盘事件不依赖元素焦点。一次按键先送达应用逻辑，再送达持有键盘的那个 Surface，各自执行自己的链：

- 屏幕上有模态图层时，最上面的模态图层持有键盘，其他 Surface 都收不到按键
- 否则由当前 Page 持有。非模态的图层永远不会拿走键盘，所以它下面的 Page 仍然收得到按键
- 剧情显示在屏幕上、且上面没有 Page 或模态图层时，键盘归舞台所有，舞台上除`notification`插槽以外的每个游戏界面都会收到按键

持有键盘的 Surface 上的控件通过自己的键盘 Head 收到按键，其他 Surface 上的控件收不到

Surface 从显示出来的那一刻起、贯穿进入动画都能收到按键，并在退出动画开始时停止。想在 Surface 仍在进场时忽略按键，在图里用 App 分类的`Is Surface Entering`分支

只想匹配一个绑定时用带过滤的一对，想拿到按键本身时用`Any Key`一对：`On Key Down`/`On Key Up`匹配卡片上配置的绑定且不携带 payload，而`Any Key Down`/`Any Key Up`对每个按键都触发，并给出`key`和各修饰键状态

## 输入意图

### On Action

`blueprint.event.head.action`

On Action（意图触发时）在卡片上选中的那个输入意图被触发时触发，不论玩家是怎么触发的。

意图是项目给某个手势起的名字——“推进”“打开记录”“取消”——而它背后的绑定写在项目的意图词表上、以及每个 Surface 对它的回应里，从来不写在图上。这正是这个 Head 存在的意义：作者按名字选意图，至于哪个键、哪次点击算数，那是项目的事。卡片存的是意图的 id，所以给意图改名不会让任何图失去指向。

只能用于应用逻辑与 Surface 的图。一个意图按其构造就是整块面板范围的，所以它属于那两个能代表整块面板的宿主：Surface 回答它启用了哪些意图，应用逻辑回答那些在每一页上含义都相同的手势。一个控件说“在我这里点一下就是推进”，正是词表要取代的那种安排——想要原始手势的元素仍然有它自己的鼠标 Head。

应用逻辑会收到词表里的每一个意图，并且先于任何 Surface。不论哪个 Surface 持有键盘，它都会收到按键；不论指针手势落在哪里，它都会收到。Surface 只收到它回应的那些意图：按键在它持有键盘时，指针手势在落到它上面时。两边都回应同一个意图时，两边都会执行。本来是冲着控件去的输入，两边都收不到：落在按钮、开关、滑块、文本输入框或 List 上的指针手势不会触发意图（滚轮落在已经无法朝那个方向继续滚动的 List 上时除外），获得焦点的控件自己会处理的按键也不会，例如焦点在按钮上时按 `Enter`。按住不放的按键只触发一次意图。

| 引脚 | 方向 | 类型 | 说明 |
| --- | --- | --- | --- |
| `then` | out · exec | — | |
| `source` | out · data | `string` | 是哪一类输入触发的：`pointer`、`key`、`gamepad` 或 `touch` |
| `x` | out · data | `float` | 手势落点，与鼠标 Head 用的是同一套坐标 |
| `y` | out · data | `float` | |

**卡片字段**

| 字段 | 说明 |
| --- | --- |
| `Action` | 项目的输入意图之一 |

对按键和手柄绑定来说 `x` / `y` 没有意义，在那里读作 `null`。这正是 `source` 紧挨着它们的原因：它就是那个说明另外两个有没有意义的引脚。同一个意图确实会因来源不同而想要不同的行为：来自一次点击的“推进”有一个屏幕上的位置可以回应，来自空格键的没有。

要问某个意图**是否正被按住**而不是对它被触发做出反应，用 [Input](/zh/docs/studio/blueprint/nodes/input) 里的 `Is Action Held`。

### Send Broadcast

### Get Listener Count

`blueprint.broadcast.getListenerCount` · Pure

Get Listener Count（获取监听器数量）读取当前 Surface 上某个广播事件名已注册的监听器数量

统计的是 **Head** 而不是蓝图：一张图里有两个匹配 Head 就计两次，一个`On Any Broadcast`对每个事件名都计数。Head 从文档中统计，因此当前未挂载的元素同样计入
