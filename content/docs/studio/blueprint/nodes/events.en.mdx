An event head is where a graph begins. It has no execution input — the runtime enters the graph at the head and the chain runs from `then`. Everything else on this page hangs off that: a head's data outputs are the event's payload, and which heads you are even offered depends on where the blueprint lives.

## Conventions

- **A head has no exec input.** There is nothing to wire into it. A graph may hold several heads, and each one runs its own chain when its event arrives. Every head listening for the same event, in one graph or in several, starts when the event arrives; none waits for another to finish, and one that fails does not stop the rest. Where the game waits for an event, as start-up waits for [`On Game Ready`](#on-game-ready), it waits for all of them.
- **Data outputs are the payload.** Every output pin other than `then` reads one field of the runtime event payload, keyed by the pin id. A field the dispatch did not set reads `null` — not `0`, not `""`.
- **Coordinates are design coordinates.** An element's mouse heads report the element's own local design space. So does a head that runs because a press [climbed](#event-bubbling) from a descendant: it reads the point the press landed on in its own element's box, not in the box of the element under the pointer. `Mouse Click` and `Right Click` placed on a Surface blueprint report that [Surface](/docs/studio/blueprint/surfaces)'s design space instead.
- **Blueprint Value heads.** A Blueprint Value graph accepts exactly two heads: `Init` and `On Flush`.
- **A disabled element stays silent.** A widget that is disabled, or in text-editing state, does not dispatch its interaction heads at all.

## Where a head is offered

The palette filters heads by the blueprint's owner. A head that is not listed for your owner is not hidden behind a setting — it does not exist there.

| Owner | Heads offered |
| --- | --- |
| Global blueprint (`globalMain`), listed as **App logic** | `App Boot`, `On Game Ready`, `On Fullscreen Changed`, `On Window Focus Changed`, `On Window Close Requested`, `On Action`, the four keyboard heads, both preference heads |
| Surface blueprint (`surfaceMain`) | `Surface Init`, `Surface Unmount`, `Before Surface Exit`, `After Surface Enter`, `Mouse Click`, `Right Click`, `On Fullscreen Changed`, `On Window Focus Changed`, `On Window Close Requested`, `On Action`, the four keyboard heads, both preference heads, both broadcast heads, `Element Flush`, `Element Click` |
| Widget blueprint (`widgetMain`) | whatever that widget type declares; see the table below |
| Widget inside a component definition (`componentWidgetMain`) | `Init`, `On Flush`, `Unmount`, `Before Surface Exit`, `After Surface Enter` and the heads its type declares in the table below. No keyboard, window, broadcast or bound element heads. |
| Blueprint Value (`widgetValue`) | `Init` and `On Flush` |
| Story action blueprint | `On Call` |

For a widget the owner is only half the rule: each built-in widget type declares a set of event capabilities, and a head appears only if the widget's own capabilities list it. That is why a `nl.list` offers no `Mouse Enter` and a `nl.container` offers no `Item Click`.

| Widget type | Heads |
| --- | --- |
| every widget with a private blueprint | `Init`, `On Flush`, `Unmount`, `Before Surface Exit`, `After Surface Enter`, the four keyboard heads, `On Fullscreen Changed`, `On Window Focus Changed`, `On Broadcast`, `On Any Broadcast`, `Element Flush`, `Element Click` |
| `nl.container`, `nl.text`, `nl.image`, `nl.button`, `nl.dialog.sentence`, `nl.nvl.texts` | the nine mouse heads, `Focus`, `Blur`, `List Item Refresh` |
| `nl.video`, `nl.puppet` | the nine mouse heads, `Focus`, `Blur` |
| `nl.switch` | the nine mouse heads, `Focus`, `Blur`, `Changed`, `Turned On`, `Turned Off` |
| `nl.list`, `nl.notification.list`, `nl.choice.list`, `nl.nvl.list` | `Scroll`, `Scroll End`, `Item Render`, `Item Click`, `Item Hover`, `Selection Changed` |
| `nl.slider` | `Drag Start`, `Value Changed`, `Drag End` |
| `nl.textInput` | `Value Changed`, `Submit`, `Focus`, `Blur` |
| `nl.frame` | `Page Event` |

One further narrowing applies inside a widget blueprint: `List Item Refresh` is offered only when the element actually sits inside a List item template.

## Event bubbling

Six pointer events climb the element tree: `Mouse Click`, `Mouse Double Click`, `Mouse Down`, `Mouse Up`, `Mouse Wheel` and `Right Click`. The event starts at the element under the pointer and passes through each parent in turn, up to the root of the Surface that element is drawn on. Every element on that path that has a head for the event runs it, and an element without one is passed over. An element with a head does not keep the event: its ancestors' heads run as well. Each head runs its own chain, so do not build a graph that depends on which of them runs first.

- **What does not climb.** `Mouse Enter`, `Mouse Leave` and `Mouse Move` stay on the element the pointer is over. Keyboard, focus, flush and lifecycle events do not climb either, and neither do a widget's own events (`Item Click`, `Value Changed`, `Changed`, `Submit` and the rest).
- **Widgets without mouse heads.** A list, slider, text input or frame offers no mouse heads and passes the six events up like any element without a head, so a container with a `Mouse Wheel` head hears the wheel over a list inside it.
- **Leaving a list.** Inside an item template, a head runs for the row under the pointer. When the event climbs out of the list, that row is left behind: the elements above the list run with their own variables and read no row item.
- **Leaving a component.** From the root of a component, the event continues at the element that placed the component, so a container holding a placed component hears presses on it.
- **The Surface.** A click that reaches the Surface also runs the Surface blueprint's own `Mouse Click` or `Right Click`.
- **A Page in a Frame.** A press on an element of a Page shown in a Frame climbs to the root of that Page and no further: the Frame and the elements around it do not hear it. The shown Page runs its own Surface `Mouse Click` or `Right Click` for the press, in its own design space, and then the Surface holding the Frame runs its own. A press on an empty part of the shown Page belongs to the Frame and climbs from there.

A graph cannot end the climb early. A [script](/docs/studio/scripts) layer can, with `ctx.stopPropagation()`: the elements above do not hear the event, and the other heads on the same element still run. The heads of one element start together, and the climb moves on to its parent once they have finished. The nodes that used to steer bubbling, `Continue Event Bubble` and `Stop Event Bubble`, were removed. The one thing they were reliably used for, holding a window close open, is now [`Keep Window Open`](/docs/studio/blueprint/nodes/app) in the App category, which does that and nothing else.

The global blueprint has no mouse heads. It hears pointer input through [`On Action`](#on-action), wherever the gesture lands, including where no interface takes it: a Page takes a press only where one of its elements is drawn, so a press on an empty part of a Page, or on a stage with nothing on it, still reaches the global blueprint's `On Action` heads.

While a Page or layer plays its exit animation, a press that no Page or layer takes is dropped. It does not reach the game stage or the Game UI on it, so it does not advance the story, and the global blueprint does not hear it. A press on the Page arriving in its place reaches that Page as usual. The same holds inside a Frame while it changes page: the arriving Page's elements answer presses as usual, and no press goes further than the Frame, so none becomes a click on the Frame, the elements around it or the Surface.

<Callout type="warn">
While focus is in a text-entry element, keys reach no blueprint at all: the global, Surface and widget keyboard heads do not run and no input action is raised, so typing a name cannot advance dialogue on Space or open the menu on Escape. The field's own `Value Changed` and `Submit` heads still fire.
</Callout>

### On Game Ready

`blueprint.event.head.gameReady`

Fires once per accepted NarraLeaf session: the `LiveGame` object exists and is stored in the Studio runtime, but `liveGame.newGame()` has not started the first scene yet.

The runtime initialises the NarraLeaf environment as a boot step, *before* the Surface system comes up. It mounts a Player on the compiled story of the Story library's default story entry scene, so `LiveGame` exists and that scene's assets begin preheating while the player is still on the main menu. Actually entering the game happens only on `Start Game` or a load, and it reuses that same initialised `LiveGame`: when `Start Game` targets the already-preheated default scene, entry is instant and this head does **not** fire again. Only a `Start Game` aimed at a different scene remounts the environment and fires it a second time. With no default story configured, an empty environment is mounted and the head still fires at boot.

| Pin | Direction | Type | Notes |
| --- | --- | --- | --- |
| `then` | out · exec | — | |

<Callout type="info">
Initialise NarraLeaf preferences here — `Set Auto Forward`, `Set Game Speed`, `Set Voice Volume`, `Set Sentence Speed` — so they are in place before the player enters a game. Not in `App Boot`: despite the name it does not run first (`On Game Ready` fires ahead of it), and it carries no guarantee that a live game exists.
</Callout>

### On Fullscreen Changed

`blueprint.event.head.fullscreenChanged`

Fires when the application window enters or leaves fullscreen, including a change made outside the game. It reaches the global blueprint first, then every Surface on screen: the layers from the topmost down, the current Page, any Page shown in a Frame, and the Game UI Surfaces on the stage. On each of those Surfaces, every widget blueprint that places the head runs too. That is why a settings control can track the window without owning the Page.

| Pin | Direction | Type | Notes |
| --- | --- | --- | --- |
| `then` | out · exec | — | |
| `isFullscreen` | out · data | `boolean` | The state after the change. |

### On Window Focus Changed

`blueprint.event.head.windowFocusChanged`

Fires when the application window gains or loses focus, for example when the player switches to another program and back. A desktop build follows its own window, which includes the window being sent behind by something outside the game; a web export follows the page's visibility and focus. It reaches the same blueprints as `On Fullscreen Changed`, in the same order. It is unrelated to the widget `Focus` and `Blur` heads, which are about which control holds the keyboard focus.

To read the current state from a graph that runs for some other reason, use `Is Window Focused` in the [App nodes](/docs/studio/blueprint/nodes/app).

| Pin | Direction | Type | Notes |
| --- | --- | --- | --- |
| `then` | out · exec | — | |
| `isFocused` | out · data | `boolean` | The state after the change. |

### On Window Close Requested

`blueprint.event.head.windowCloseRequested`

Fires when the player asks to close the window. The close is held open while the global blueprint runs and then each Surface on screen, in the order `On Fullscreen Changed` describes. A `Keep Window Open` in any of them cancels the close, and the Surfaces after it are not asked. Absent one, the window proceeds to close. In Dev Mode this covers the Dev Mode window; in preview and production, the game window.

Global and Surface blueprints only.

| Pin | Direction | Type | Notes |
| --- | --- | --- | --- |
| `then` | out · exec | — | |

## Element lifecycle

### Init

`blueprint.event.head.init`

Fires once when an element that supports a private blueprint has completed its first render and mounted. It is not a pre-render hook. A Dev Mode bundle revision that remounts the Surface or the element fires it again. In a Blueprint Value it is the initial evaluation entry; later evaluations come from the hidden Element property dependencies, from a write to any variable the last evaluation read, or from an explicit `On Flush`.

| Pin | Direction | Type | Notes |
| --- | --- | --- | --- |
| `then` | out · exec | — | |

### Unmount

`blueprint.event.head.unmount`

Fires when the element leaves the runtime element tree: the Surface closes or is replaced, a Frame switches sub-Page, a List item instance is removed, or visibility stops the element rendering at all. Runtime `display: none` only hides the element and keeps it mounted, so it does not fire.

| Pin | Direction | Type | Notes |
| --- | --- | --- | --- |
| `then` | out · exec | — | |

### On Flush

`blueprint.event.head.flush`

Fires when this blueprint's own element has a property changed explicitly through the blueprint Host API and that change causes a redraw. Automatic CSS state styling — a hover or focus variant computed by the renderer — does not fire it. In a Blueprint Value it doubles as an explicit re-evaluation entry: the default Dialog Nametag refreshes as the dialogue advances through this head, without the Dialog remounting.

Flush is a batched post-commit notification. The runtime coalesces flushes for one element per frame, and a flush handler that writes to the element again lands its new flush in the *next* frame's batch — there is no synchronous re-entry.

| Pin | Direction | Type | Notes |
| --- | --- | --- | --- |
| `then` | out · exec | — | |
| `element` | out · data | `element` | The element that was flushed. |

## Keyboard

Keyboard events do not depend on element focus. A key goes first to the global blueprint, then to the Surface that owns the keyboard, and each runs its own chain:

- With a modal layer on screen, the topmost modal layer owns the keyboard. No other Surface hears keys.
- Otherwise the current Page owns it. A layer that is not modal never takes the keyboard, so the Page beneath it keeps hearing keys.
- While the story is on screen with no Page or modal layer over it, the keyboard belongs to the stage, and every Game UI Surface there hears the key except the `notification` slot.

The widgets on the Surface that owns the keyboard hear the key through their own keyboard heads. Widgets on any other Surface do not.

A Surface hears keys from the moment it is revealed, through its enter animation, and stops when its exit animation begins. To ignore keys while a Surface is still entering, branch on the App category's `Is Surface Entering`.

Pick the filtered pair when you want one binding, and the `Any Key` pair when you want the key itself: `On Key Down` / `On Key Up` match a binding configured on the card and carry no payload, while `Any Key Down` / `Any Key Up` fire on every key and hand you `key` plus the modifier flags.

## Input actions

### On Action

`blueprint.event.head.action`

Fires when the input action picked on the card is raised, however the player raised it.

An action is a name the project gives to a gesture — "advance", "open the log", "dismiss" — and the bindings behind it live on the project's action vocabulary and on each Surface's answer to it, never on the graph. That is the point of the head: the author names the action, and which key or click means it stays the project's business. The card stores the action's id, so renaming the action leaves every graph pointing at it.

Global and Surface graphs only. An action is panel-wide by construction, so it belongs to the two owners that speak for a whole panel: a Surface answers the actions it enables, and a global blueprint answers a gesture that means the same thing on every page. A widget saying "a click here means advance" is the arrangement the vocabulary replaced — an element that wants the raw gesture still has its own mouse heads.

The global blueprint hears every action in the vocabulary, before any Surface answers it. It hears a key whichever Surface owns the keyboard, and a pointer gesture wherever it lands. A Surface hears only the actions it answers: a key while it owns the keyboard, and a pointer gesture that lands on it. When both answer the same action, both run. Neither hears an input that was meant for a control. A pointer gesture on a button, switch, slider, text input or list raises no action, except a wheel over a list that cannot scroll any further that way, and neither does a key the focused control acts on, such as `Enter` on a focused button. A key held down raises its action once.

| Pin | Direction | Type | Notes |
| --- | --- | --- | --- |
| `then` | out · exec | — | |
| `source` | out · data | `string` | Which family of input raised it: `pointer`, `key`, `gamepad`, or `touch`. |
| `x` | out · data | `float` | Where the gesture landed, in the same coordinates the mouse heads report. |
| `y` | out · data | `float` | |

**On-card fields**

| Field | What |
| --- | --- |
| `Action` | One of the project's input actions. |

`x` and `y` are meaningless for a key or a gamepad binding and read `null` there, which is why `source` sits beside them: it is the pin that says whether the other two mean anything. The same action legitimately wants different behaviour depending — "advance" from a click has a place on screen to answer at, and "advance" from the space bar does not.

To ask whether an action is *being held* rather than react to it being raised, use `Is Action Held` in [Input](/docs/studio/blueprint/nodes/input).

## Game preferences

Both heads subscribe to the active `LiveGame`'s preference dispatcher. They are offered on global and Surface blueprints, and a change reaches the global blueprint and then every Surface on screen, in the order [`On Fullscreen Changed`](#on-fullscreen-changed) describes. With no live game running there is no subscription and nothing fires; after `On Game Ready` the runtime re-subscribes on the new `LiveGame`. Preference setters like `Set BGM Volume` and NarraLeaf's own internal writes both trigger these heads, and a write of an identical value is not guaranteed to be deduplicated — so do not write a preference from the graph that listens to it, or you build a self-triggering loop. See the [Game nodes](/docs/studio/blueprint/nodes/game) for the getters and setters.

### On Preference Changed

## Broadcast

Broadcast moves a named message between blueprints on the Surface it is sent from: the Surface's own blueprint plus every widget blueprint on it. A widget that a List repeats hears it once in each row on screen. It does not reach the global blueprint and does not cross Surfaces, and the sender receives its own broadcast if it also listens. Targets are resolved from the document, not from the mounted React tree. All four nodes are offered on Surface and widget blueprints only.
